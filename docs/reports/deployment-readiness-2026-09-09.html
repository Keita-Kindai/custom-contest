P0 · 認可

同時作成で他ユーザーのセットを上書きできる

Routeは先に ownerOf(setId) を読み、存在しなければ新規作成として通す。その後の INSERT ... ON CONFLICT DO UPDATE はowner条件なしで同じIDを更新する。2アカウントが同じ未使用IDへ同時PUTすると、両方の所有者確認がnullになり、後着が先着所有の内容を更新できる。

完了条件: 作成は衝突時409、更新は WHERE owner_id = session user をDB内で原子的に保証する。1 transaction内の行lockまたは条件付きUPDATEを使い、競合テストを追加する。

データベース設計の評価

良い点

公開範囲はserver queryで判定

privateを画面で隠すだけにせず、本人以外にはnull/404を返す。owner/user IDもclient入力ではなくAuth.js sessionから取る。

良い点

整合性制約とcascadeが具体的

foreign key、unique、CHECK、transaction、owner削除時cascadeがある。問題カタログ参照もrestrictされ、孤児データを防ぐ。

良い点

通信暗号化を明示的に強制

Neonの sslmode=require を verify-full へ固定し、将来のpg解釈変更で証明書検証が弱まることを防ぐ。Vercelではpool max=1。

修正

health checkが最新migrationを見ない

REQUIRED_MIGRATION は0001だけで、0002〜0004欠落でもhealthyになり得る。最新version、全必須version、seed件数を検査する。

修正

migration履歴と実DDLが弱く結び付く

全SQLを毎回実行して最後にversionを記録する形で、checksumはない。適用済みfileの改変検知、advisory lock、forward-only方針を加える。

修正

無料枠はバックアップではない

Neon Freeの復元履歴は最大6時間。翌日気づく論理削除には足りない。ユーザーデータ消失を許容するとしても、運営者が説明した保持方針との不一致や不正削除の証拠喪失は残る。

AtCoder / AtCoder Problemsの評価

精進側だけなら、runtimeでAtCoderへ自動取得はしない。 固定JSONを検索し、問題名からAtCoderへリンクする。問題文・提出コード・cookieをCustom Contestへ送らないため、影響をかなり抑えている。ただし、データ生成時のAPI利用条件と、Duel公開時の提出監視は別問題である。
精進側

公開前にAPI間隔を修正し、出典を表示

APIの1秒超間隔を守る。AtCoder Problemsが非公式でDifficultyも非公式推定であることをUI/規約に明示する。MIT Licenseはrepository softwareのライセンスであり、AtCoder由来の全データに包括的な再利用許可を与えるものと断定しない。

Duel側

一般公開前にAtCoderへ問い合わせ

提出一覧HTML/status JSONの自動取得は、公開APIとしての許可・数値上限を確認できない。本人セッション・低頻度でも自動的に許可済みにはならない。用途、最大同時人数、endpoint、頻度、field、非営利性、障害時停止を示して公式回答を得る。

userscript

多重tabと無期限pollを止める

@match がAtCoder rootだけでもroot tabを複製でき、timerはtab内変数なので通信が倍増する。Custom Contest障害時に古いactive Matchが残り、期限なしにAtCoderをpollし得る。browser内leader lease、共通request queue、server疎通TTL、deadline停止を入れる。

利用形態

企業・採用・商用へ広げない

AtCoderは企業開催イベントで過去問を使うcontestとcoding testを禁止し、勉強会も採用活動と組み合わせないよう示している。個人の無料練習サービスへ一律適用されるとは断定できないが、収益化・企業利用時は直接の停止条件になる。

法務・規約の確認結果

個人情報保護法

小規模・無料でも、反復継続してサービスを提供する個人情報取扱事業者になり得る。OAuth email等は個人情報であり、DBで検索可能な体系に入れば個人データに当たり得る。少なくとも利用目的の特定・通知/公表、安全管理、委託先監督、本人対応、漏えい時対応を準備する。一定の漏えい等ではPPC報告と本人通知が必要で、速報は概ね3〜5日以内が目安とされる。

Vercel/Neon等への保存が常に「外国第三者提供の同意」を要するとは限らず、委託として整理できる場合がある。ただし、保存国、契約、再委託、安全管理を確認し、公表内容へ反映する。個別の契約構成は専門家確認が必要。

Google / GitHub OAuth

Google OAuthポリシーは、公開アプリのホームページに機能説明と利用規約・プライバシーポリシーへのリンクを求める。client secretは厳重に管理し、正確なapp identityと最小scopeを使う。GitHubもcallback URL、privacy URL、運営者情報を実態と一致させる。現状のDBはprovider tokenも保存するため、利用しないtokenを保持し続けない設計を検討する。

著作権、商標、ユーザー投稿

問題文や提出コードを複製せず、タイトル・ID・link中心なのはよい。とはいえAtCoder規約はサイト構成物の権利がAtCoderまたは権利者に帰属するとするため、「公開データだから自由利用」とは扱わない。AtCoder公式ロゴは現状見当たらない。将来使う場合、ガイドラインはサービス利用時に連絡を求める。

ユーザーがタイトル・説明を公開投稿できるため、第三者の問題文転載、侮辱、個人情報、違法情報、spamに対する禁止条項、通報、非公開化、削除、異議対応を決める。初期規模でも問い合わせ先は必要。

電気通信事業法の外部送信規律、未成年、商用化

OAuth、hosting、将来のanalytics/cookie等で利用者端末から第三者へ情報を送る場合、外部送信規律の対象サービス・情報に該当するかを確認し、該当するなら送信先、情報、目的の通知・公表等を行う。現状はanalytics/広告SDKを導入していないため範囲は小さい。

AtCoder利用者には未成年も想定される。規約同意、公開表示名、問い合わせ・削除方法を分かりやすくする。課金を始める場合はVercel Hobbyから移行し、特定商取引法表示、返金、税務、決済委託を別監査する。

今日進める場合の順番

公開境界を「精進側のみ」に固定

Battle画面のredirectに加え、Battle・Match・userscript APIをproduction flagで停止。userscript非配布、Fake evidence無効を検査する。

P0のコード2件を修正

problem setの所有者競合を原子的に防ぎ、catalog生成を1.1秒間隔の逐次取得へ直す。競合testと取得順testを追加する。

公開文書と窓口を用意

プライバシーポリシー、利用規約、問い合わせ先、削除申請方法をfooterとOAuth homepageから1回で到達可能にする。運営者名/連絡先は実在するものを入れる。

本番環境を分離・固定

ProductionとPreviewのDBを分ける。AUTH_SECRETを生成し、OAuth callbackを本番originへ限定。DATABASE_URLはpooled + sslmode=verify-full、Fake flagはunset。

本番相当DBで検証

空DBへ0001〜0004 migrationと3295問seedを適用。11 integration test、2アカウント認可、OAuth sign-in/out、private/unlisted、削除cascade、cold startを確認する。

濫用と障害の最低限を入れる

rate limit、件数上限、pagination、usage alert、error monitoring、kill switchを設定。security headers（CSP、Referrer-Policy、X-Content-Type-Options等）を追加しproduction responseで確認する。

バックアップと事故対応を試す

日次pg_dumpを本番DBと別の場所へ暗号化保存し、復元を一度行う。漏えい・不正投稿・DB停止・OAuth secret漏えいの連絡/停止手順を1ページにする。

限定公開から段階的に開く

まずアクセス制限付きPreviewで友人2〜5人、次に招待制production、最後に一般公開。一般公開前にproduction smoke testと費用上限を再確認する。
